Gene, 2026-09-28, verbatim:

> "this tool needs to be smart enough to understand surfaces and different surfaces
> probably need a sub-categorization that can act as part of the repo. and can still
> count as a single turn, obviously, but different parts can get cycled through and

> look at and focus on them, right? So for an app that has a web app and an Android

**The requirement in one line:** a *surface* cycles WITHIN a project; the project
still counts as ONE visit in the rotation.

## 1. The measured problem

`improve.yaml` declares `surfaces: server, android, chrome-extension` for secondbrain
(line 109). **Nothing consumes it.** A repo-wide grep for `surfaces` returns 29 hits and
every single one is either a *different* producer (`repo_brief.py` builds its own list
from the survey; `repo_survey.py:193` via `_multi_surface()`) or an unrelated English
sentence in a prompt ("a change that surfaces it"). The manifest line is **pure
documentation**, which is precisely why it drifted.

Three sources disagree:

| Source | Surfaces | Count |
|---|---|---|
| `improve.yaml:109` (hand-written) | server, android, chrome-extension | 3 |
| `repo_brief.py` (LLM, from `state/repos/secondbrain.json`) | server (FastAPI + web app), android app, chrome extension | 3 |
| Gene | web server, web app, chrome extension, android app, **android assistant/recorder** | 5 |

**The recorder app is invisible to the tool.** `'assistant' in improve.yaml` → `False`.
The LLM brief did not find it either. It lives inside `android/` (verified: `android/app/`
only), so a directory-name-based survey cannot split it from the phone app that hosts it.

**Why this matters beyond bookkeeping:** Gene's recording-buffer bug lives in a surface
the loop does not know exists, so no round could ever have been aimed at it.

## 2. Where a surface belongs (verified by reading, not assumed)

The rotation is a project list mirrored into `state/rotation.json` by
`loopctl.py:76 _sync_rotation()`; `angles_per_visit` (`loopctl.py:39`, default 2)
controls how many angles one visit gets.

The actual "what will this round work on" decision is:

- `karpathy_runner.py:269` — `angle = angle_pick.pick(name, facts=facts)`

A surface is a SECOND axis at that exact point, and the runner already persists the
angle for the panel at `karpathy_runner.py:301 entry["current_angle"]`. So the surface
is stored beside it and the round prompt gains a surface scope line.

**The cycle is per (project, surface), not per project:**
`next_surface = surfaces[(index_of(last_surface) + 1) % len(surfaces)]`
— so secondbrain rotates server → web-app → chrome-ext → android → recorder → server.
The project still advances normally; only the frontier inside it moves.

## 3. Reconciliation: the MANIFEST is authoritative — I had this backwards

**Correction (2026-09-28):** my first draft of this file argued the brief was authoritative
and the manifest merely an override. That is **wrong, and the code says so:**

- `karpathy_runner.py:458` `m = I.load_manifest()` → `:468` `projs = I.enabled(m)` →
  `:475` `sorted(projs, key=lambda p: reg.get(...)["last_nudge"])`. The runner's entire
  input is the manifest. `loop.json` appears only as an *upsert source* (`:459`,
  "Picker wrote a name into loop.json that improve.yaml lacks? Upsert a…"), never as
  the pick path.
- `angle_prompts.py:187` `rec = d.get(project)` — the prompt cycle is keyed by project
  name alone.

So anything the rotation consumes **must live in `improve.yaml`** or it breaks the
architecture's own rule (the karpathy-loop skill: "the runner reads improve.yaml only").
A "smart" runtime merge of brief-discovered surfaces would create surfaces the rotation
can never actually reach.

**The deterministic rule:**

1. `surfaces_for(proj)` starts from the manifest's `surfaces:` list. That is the frontier.
2. A surface found in the brief but absent from the manifest is **proposed, not adopted**:
   the runner logs it and (once per surface) notifies — *"brief found surface
   'android-assistant' not in improve.yaml — add it or ignore"*. Rotation never silently
   moves onto an undeclared surface.
3. A manifest surface with no brief counterpart **stays** — the brief may be stale.
4. Match by canonical slug, not free text: brief names are prose
   (`"server (FastAPI API + web app)"`), manifest names are ids.

### Why the recorder was invisible — measured, not guessed

`repo_survey.py:174-180`:

```python
def _multi_surface(root: Path, top_dirs: dict) -> list[str]:
    known = ("server", "android", "chrome-extension", "web", "app", "client", ...)
    return [d for d in known if d in top_dirs and top_dirs[d] > 0]
```

It returns only names from a **hardcoded allowlist of TOP-LEVEL directory names**. The
recorder lives inside `android/` (verified: `android/app/` only), so it is *structurally
impossible* for this detector to see it. The detector cannot express "two apps inside one
directory" — so no amount of re-running the brief would ever find Gene's assistant app.

**Consequence:** the fix is not a smarter detector. The surface must be declared in the
manifest by hand, and the tool's job is to *tell Gene when it finds one he missed*, which
is the notification in rule 2.

## 4. Per-surface `see:` — so each surface can actually be LOOKED at

Today one `see:` block per project, with a flat `surfaces:` string beside it. The
surfaces are not equally viewable and the single block cannot say so:

| Surface | How you look at it |
|---|---|
| web server | `http://127.0.0.1:8823/health` — a live URL, 401 without the bearer |
| web app | a page **inside** that server, not its own port |
| chrome extension | not URL-addressable at all — load-unpacked from `chrome-extension/` |
| android app | not URL-addressable — a device install |
| android assistant/recorder | same, and this is where the bug is |

So `see:` gains a `surfaces:` list, each entry carrying its own viewability. The
existing flat `see.url`/`see.kind`/`see.start` **stays** as the project-level default,
so every current consumer (`activity.py:_see_for`, the widget's two `href` sites)
keeps working unchanged.

## 5. Payload budget — the hard constraint

The bridge CLIPS at ≈4,000 B and the payload already ships **3,297 B**
(`activity.py --selfcheck`). So per-surface data must be tiny and must not be sent for
every project: send surfaces **only for the current project**, names only, and let the
`see:` detail ride along only where it already exists per project.

## 6. Gene's refinement (2026-09-28) — the parallel-update requirement

Verbatim:

> "each surface can be worked on separately so that it can be... we can cycle through
> surfaces and then cycle through as i said angles and so if you want to come up with a
> fair way to cycle through surfaces Maybe we just round robin the surfaces so that they're
> all getting a good look and fair update time, I suppose. And there may actually be things
> that need to be done that are done on one surface that need to be done on another. And if
> that's the case, we need something in our surface logic that allows one turn to update all
> surfaces if needed so that things stay parallel with each other if needed... So we're not
> going to break them out just for the sake of breaking them out. We'll break them out where
> separate looking at the code makes sense. But at the same time, if all surfaces need to be
> worked on, because one has updates we found and identified that need to be done on all
> surfaces, then they need to be done at that time."

Three requirements, and the third is the hard one:

1. **Round-robin surfaces** so each gets fair look time.
2. **Recursive pairing:** cycle surfaces, and within each surface cycle the angles (the
   existing 168-prompt table).
3. **A PARALLEL/COORDINATED MODE:** one turn must be able to touch ALL surfaces at once
   when a change is cross-cutting. This is not decoration — breaking a repo into surfaces
   naively *causes* drift (the web app learns a new API field, the Android client never
   does). The parallel mode exists to prevent exactly that drift.

### 6.1 Surface rotation — round-robin with fair time

State per project: `{order: [...slugs], cursor: int, last_surface: str, visits: {slug: n}}`.

- Normal round: `next = order[(index_of(last_surface) + 1) % len(order)]`.
- Using round-robin rather than "least-visited" matters because surfaces are **not
  symmetric**: `android-assistant` has far more work than `chrome-extension`. Round-robin
  gives every surface a guaranteed turn even when one is boring; least-visited would let a
  high-churn surface starve the others. Round-robin, exactly as Gene asked.
- The project still advances once per round (`last_nudge` at `karpathy_runner.py:355`
  is untouched), so **a surface is never a rotation slot** — it is a frontier inside one.

### 6.2 The parallel mode — REVISED after adversarial review (2026-09-28)

**The original design was wrong. An adversarial reviewer found it, I verified it, and it
is recorded here rather than quietly deleted.**

#### What was wrong

The first design made a parallel round "one child that touches all surfaces." Two measured
facts kill it:

1. **`ROUND_TIMEOUT = 4200` s (70 min)** — `karpathy_runner.py:57`, with the comment at
   `:54` reading *"Rounds normally take 50-60 min; this is generous"*. A 5-surface serial
   round is 250-300 min. It gets killed.
2. **The kill path does not roll back.** On timeout, `rc=124` and **`last_nudge` still
   advances** (`:355`), so the loop rotates onward with a half-finished cross-cutting edit
   sitting in the worktree. The wedge detector will not fire either (`loopctl.py:133`'s
   stale threshold is 2× timeout, and a landed `last_nudge` suppresses it).

So the parallel turn would not *prevent* drift — it would **guarantee half-applied drift on
a timer, silently.** That is worse than not having the feature.

#### The revision: parallel is a CAMPAIGN, not a single round

Instead of one giant child, a cross-cutting change becomes **N consecutive rounds sharing
one checklist**, which the existing timeout / kill / checkpoint machinery already handles
unchanged:

- `entry["campaign"] = {"id": <slug>, "surfaces": [...], "verdicts": {slug: verdict}}`
- The runner sets `scope: campaign` for each subsequent round of that project until every
  surface carries a verdict (`done` / `deferred+why` / `not-applicable+why`).
- Each round still does **ONE finding** (the template's hard rule at `round_prompt.py:37`),
  scoped to one surface. The parallel *intent* is preserved; the parallel *blast radius*
  is not.
- The project still counts **one visit per round** — `last_nudge` semantics untouched.
- A campaign may not be marked complete while any surface is unaccounted for. That check is
  mechanical in one respect only: the verdict map must be full. **Per-surface `done` remains
  a claim, not a verified fact** — there is one project-level `gate:` command
  (`karpathy_runner.py:231-235`), so the runner cannot independently verify each surface.
  Say that plainly rather than implying more rigor than exists.

#### The marker (still needed, and these are the two halves the first plan omitted)

1. **The prompt must ASK for it.** `round_prompt.py`'s TEMPLATE (`:12-49`) never requests a
   `CROSS_CUTTING:` line. A marker nobody is asked to emit does not arrive. Emit it as a
   **required final line**, and put it **first** in the required-lines block — the precedent
   is unkind: the already-mandated `REVIEW()` line (`round_prompt.py:31`) appeared in **0 of
   3** recent substantive round sessions.
2. **Parse the FULL output, not the tail.** The runner captures the whole string at
   `karpathy_runner.py:338` (`_out`), then throws almost all of it away: `tail = (...)[-2000:]`
   (`:340`), a 2000 B round log (`:370`) and `entry["last_output"] = tail[-600:]` (`:367`).
   Measured: a real round's final message was 6,148 B and the persisted log held 2,030 B
   starting mid-word. **Parse `_out` BEFORE the slice.** A marker parsed only from `tail`
   will be found roughly when it is least needed.

#### One authoritative home for scope (the first plan had three, with no precedence)

The first draft put scope in three places — a marker→runner path, a `loopctl` flag→`loop.json`,
and a manifest `scope:` key. That is a guaranteed inconsistency. **Resolution:**

- **`entry["campaign"]` in the threads registry is the ONLY live home.** The runner owns it.
- The manifest may DECLARE a campaign to start (`scope: campaign` on a project) because the
  manifest is authoritative for rotation (`karpathy_runner.py:458, :468`) — but it is read,
  copied into the entry once, and then never consulted again.
- **`loopctl` exposes a READ-ONLY `--show-campaign`.** No flag writes scope. This avoids the
  dead plumbing the reviewer found: the runner reads `loopctl.load()` once per tick and only
  checks `.get("running")` (`:453-454`), so anything a flag wrote into `loop.json` would be
  invisible to round construction unless new plumbing were built — and putting live scope in
  `loop.json` would violate the design's own "the runner reads improve.yaml only" rule.
- **`state/surfaces/` is the ONLY home for surface rotation state.** `rotation.json` must
  never gain surface keys: `_sync_rotation` (`loopctl.py:76-87`) re-reads then overwrites
  that file on every config/start/pause/stop (`:253, :375, :400, :446`), so any un-mirrored
  key would be silently dropped and cursors would reset to head. Add a warning comment there.

### 6.3 Where it lives

Everything above is inside `run_round()` and the round's own prompt/result — **the
rotation sort, `last_nudge`, the manifest's project list, and `angles_per_visit` are all
untouched.** One round is still one visit, whatever its scope.
